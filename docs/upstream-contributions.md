# 代码同步与上游贡献

用户于 2026-10-22 明确设定：后续涉及代码改动，先提交神灯AI热点站点仓库，再同步个人 AIHOT Fork，同时向原项目提交更改。此授权长期有效，涵盖推送对应分支和创建相关贡献 PR，无需每轮重复确认；不涵盖直接合并原项目、强推默认分支或替维护者承诺接受改动。

## 仓库与顺序

1. 站点仓库：[littleweb/shengdeng.news](https://github.com/littleweb/shengdeng.news)。正式域名为 `https://shendeng.news/`，仓库名多一个 g。先完成改动和项目要求的检查，明确本轮文件，提交并同步站点仓库；涉及网站行为或内容的，等待发布并核验线上。
2. 个人 Fork：[littleweb/AIHOT](https://github.com/littleweb/AIHOT)。站点提交完成后，将本轮代码同步到对应工作分支。保留 Fork 默认分支便于跟踪上游；贡献分支使用 `fix/<问题>` 或 `feat/<能力>`，仅本站适用的代码使用 `shendeng/<改动>`。不整仓覆盖，不将站点部署切到 Fork。
3. 原项目：[KKKKhazix/AIHOT](https://github.com/KKKKhazix/AIHOT)。在 Fork 中从上游最新默认分支准备通用最小补丁、适用测试与文档，向上游默认分支提交 PR。不要直接用整站定制历史作为 PR。上游维护者决定是否合并。

## 贡献边界

- 每次先读上游当前 `AGENTS.md`、`CONTRIBUTING.md` 及涉及模块的文档；核实上游是否已有等价修复或现有 PR。
- 可复用的缺陷修复、通用能力和相应文档向上游贡献。新开关、配置入口、新功能或较大产品行为变化，先按上游要求开 Issue 说明场景；需要维护者讨论确认时，如实记录状态，再推进符合要求的 PR。
- 仅神灯站点适用的模块或静态部署实现也同步到 Fork 的独立工作分支，但不作为通用改动强行提交上游。报告本轮不适合上游的具体原因，保留补丁以便后续提炼。
- 本站品牌、新闻期刊、榜单快照、行业信源、采编口味和本维护约定留在站点仓库。密钥、Cookie、登录态、`.env`、`.data/`、私有日志及生产数据库不得同步。
- 原项目不接受外部 PR 修改的规则文件、依赖锁文件等，按其贡献规定处理；不将本站 `AGENTS.md` 或本文件作为上游规则变更提交。
- 仅新闻数据、品牌配置或本维护设定变更不触发代码贡献流程，不制造无关上游 PR；本设定从后续代码改动开始执行，不自动把既有所有定制批量提交上游。

## 验证和交付

站点按本地 `AGENTS.md` 验证；通用补丁还须在基于最新上游的独立工作目录中验证，避免本站配置掩盖问题。PR 说明具体触发条件、修改后行为、实际测试结果与相关 Issue，遵守上游一个 PR 解决一个问题的要求。

站点本地历史与远端如不相同，使用远端最新提交为父提交，只同步本轮明确文件，不强推、不覆盖后台刚发布的新内容。Fork 同步失败或上游要求未满足时，保留站点已完成的改动和真实状态，报告阻碍，不能声称三个仓库均已同步。

每次完成后报告站点提交、Fork 分支、上游 PR 链接及 CI 状态。创建上游 PR 后将其附加到当前任务；后续收到评审意见时在同一贡献分支修订。提交 PR 不代表上游已经接受或合并。
